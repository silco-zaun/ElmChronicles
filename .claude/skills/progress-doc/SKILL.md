# 진행 문서

진행 문서를 읽는 사람은 **이 대화를 보지 못한다.** 다음 세션의 Claude일 수도 있고 같은 프로젝트의 다른 팀원일 수도 있다. 그래서 문서의 가치는 대화에서만 오간 것을 옮기는 데 있다. 무엇을 왜 하기로 했는지, 무엇을 버렸는지, 조사하다 발견한 함정, 어디까지 했는지가 그것이다. 코드와 git에 이미 있는 내용은 다시 적지 않고 위치만 가리킨다.

진행 문서는 요청할 때만 만든다. 이 프로젝트는 기본적으로 진행 문서를 쓰지 않는다.

## 파일

- 위치: 프로젝트 루트의 `Docs/`
- 이름: `<작업명>_Plan.md` 또는 `<작업명>_Progress.md`. 작업명은 PascalCase 영문으로 한다(예: `AttackAbilityUnify_Plan.md`). 시작 전이고 계획이 중심이면 `_Plan`, 이미 진행 중이면 `_Progress`를 붙인다.
- 같은 작업의 문서가 `Docs/`에 이미 있으면 새로 만들지 않고 그 문서를 갱신한다.
- 한글로 쓰고, 코드 식별자·경로·명령은 원문 그대로 둔다.

## 쓰기 전에: 사실 확인

문서에는 확인한 사실만 적는다. 다음 사람은 문서를 믿고 움직이기 때문이다.
- `git status`, `git diff`, `git log`로 실제 상태를 본다. "완료"는 대화의 기억이 아니라 파일에 반영된 것만 표시한다.
- 문서에 적을 파일, 함수, 에셋 이름이 실제로 있는지 확인한다(Glob / Grep). 줄 번호는 금방 어긋나므로 함수 이름이나 코드 조각으로 위치를 가리킨다.
- 에셋(.uasset)은 바이너리라 Grep 도구에 안 잡힌다. 참조를 확인하려면 `grep -rlaE "<문자열>" --include=*.uasset Content`를 쓴다.

## 문서 구조

아래 순서를 기본으로 하고, 해당 내용이 없는 섹션은 뺀다.

````markdown
# <작업 이름>

> **다음 세션 시작 방법**: 이 문서를 읽고 → `git status` / `git diff`로 어디까지 했는지 확인하고 → [진행 상황](#진행-상황) 표에서 첫 번째 ☐ 단계부터 이어서 한다.

## 목표
한두 문장. 끝났을 때 무엇이 가능해지는지.

## 왜 바꾸나 / 배경
대화에서 나온 이유와 현재 구조의 문제. 근거가 된 코드 위치.

## 결정 사항
| 항목 | 결정 |
대화에서 정한 것과 그 이유. 고려했다가 버린 안이 있으면 왜 버렸는지도 적는다.

## 주의
조사하다 발견한 함정. 증상, 원인, 해결을 적는다. 다음 사람이 같은 구멍에 빠지지 않게 하는 섹션이다.

## 목표 구조
클래스나 데이터 구조. 결정이 끝난 핵심 시그니처나 코드 조각만 넣는다(전체 코드는 넣지 않는다).

## 진행 상황
| 단계 | 내용 | 상태 |
상태는 ☐(안 함) / ◐(진행 중) / ☑(완료). ◐이면 그 단계 안에서 끝난 것과 남은 것을 한 줄로 적는다.

### N단계: <이름>
- 작업: 바꿀 파일과 에셋, 무엇을 바꾸는지
- 빌드 / 실행 방법
- 테스트 표: | 확인 | 기대 결과 |

## 진행 방식
이 작업에서 합의한 작업 방식. 누가 코드를 입력하는지, 리뷰는 어떻게 하는지, 에셋 작업은 누가 하는지 등.

## 이후 작업 (이 계획의 범위 밖)
이번에 하지 않기로 했지만 이어지는 과제.
````

### 잘 쓰는 법

- **대화를 모르는 사람 기준으로 쓴다.** "위에서 말한", "아까 그 방식"처럼 대화를 전제한 표현은 쓰지 않는다. 날짜는 `2026-10-26`처럼 절대 날짜로 쓴다.
- **단계는 중간에 멈춰도 안전한 순서로 나눈다.** 예: 새것 추가 → 옮기기 → 옛것 삭제. 각 단계가 끝나면 빌드되고 기존 기능이 동작하게 한다. 그럴 수 없는 단계는 그 이유와 함께 "이어서 한 번에 한다"고 적는다.
- **단계마다 테스트 표를 넣는다.** 자동 테스트가 없는 프로젝트(PIE로 검증)에서는 이 표가 "이 단계가 끝났다"는 유일한 기준이 된다. 기대 결과는 눈으로 확인할 수 있게 구체적으로 쓴다. 실패했을 때 의심할 원인도 알면 함께 적는다.
- **에셋 작업은 따로 표로 정리한다.** 에셋 경로, 할 일, 담당을 적는다. 코드와 달리 diff로 보이지 않으므로 빠지기 쉽다.
- **진행 방식은 이 작업에 해당하는 것만 적는다.** CLAUDE.md나 메모리에 있는 규칙 중 이 작업에 영향을 주는 것만 골라 옮긴다.

## 갱신

- 단계가 끝나고 확인(리뷰, 테스트)을 통과하면 상태를 ☑로 바꾼다. 새로 생긴 결정이나 주의 사항도 해당 섹션에 추가한다.
- 진행 중인 작업에서 상태를 바꾸기 전에, 사용자가 원하는지 한 번 묻는다. 갱신을 미루고 한꺼번에 하길 원할 수도 있다.
- 작업이 모두 끝나면 두 가지를 한다.
  - 오래 남아야 할 구조적 지식(새 규칙, 새 클래스의 역할)은 CLAUDE.md로 옮긴다.
  - 이 문서를 지울지 사용자에게 묻는다. 끝난 진행 문서가 쌓이면 오히려 혼란을 준다.

## 이어서 할 때

1. `Docs/`에서 해당 문서를 찾는다. 여러 개면 작업 이름이나 최근 수정 시간으로 고르고, 애매하면 사용자에게 묻는다.
2. 문서와 `git status` / `git diff` / `git log`를 비교한다. 문서의 상태와 실제가 다르면 실제를 기준으로 알려 주고, 문서를 고칠지 묻는다(예: ☐인데 이미 코드가 있음).
3. 다음 단계를 문서의 "진행 방식"대로 진행한다.

## 다 쓰고 나서

사용자에게 다음을 짧게 알린다.
- 파일 링크
- 문서에 새로 담긴 중요한 내용(특히 대화 중에 말하지 않았던 발견)
- 시작 전에 사용자가 할 일이 있으면 그것(예: 미커밋 변경 정리)

진행 문서의 위치를 기억하는 메모리 항목이 있다면 새 문서를 가리키도록 함께 갱신한다.
